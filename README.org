*Overengineered Repository Governing a NixOS Ecosystem; Largely Ludicrous Experiments in Self-hosting.*

Much like a cell, my computing infrastructure consists of a collection of
specialised components, each with its own responsibilities. Some store and
organise information, others transport it, and still others provide the
machinery that keeps everything running.

Together, these machines support my personal projects and provide a growing
collection of services for myself, friends, and family. This repository
describes their configuration and coordinates their operation, using NixOS to
make the resulting ecosystem of services reproducible, maintainable, and perhaps
a bit more elaborate than strictly necessary.

Alternatively put, this is an experiment in [[https://bytes.zone/posts/clown-computing/][Clown Computing]] 🤡

Let's hope it works well!

* Setup

There are two ways to bring up a new machine. Where you can boot your own
media, build an installer image with [[file:create-installer.sh][create-installer.sh]], boot it, ssh in as root,
and run =./conf/install.sh=. Where you can't, start from the provider's own image
and convert it in place, as described in that platform's hardware module (for
instance [[file:modules/hardware-oracle.nix][hardware-oracle.nix]]).

On a machine whose state lives on a =Data= volume, the boot drive is
disposable. Service state lives under =/data/services=, and the handful of host
files a reinstall would otherwise lose (the uid/gid maps that keep file
ownership stable, and the SSH host key) are copied to =/data/host= each time the
deployed configuration activates. Should the boot drive die, replace it and run
the installer again: it mounts the existing =Data= filesystem, offers to restore
whatever it finds under =/data/host=, and the rebuilt system comes up as the same
host. Deselect the SSH key there to rotate it, in which case the secrets need
re-encrypting to the new key.

* Deploying

From =nix develop=, run =deploy .#<machine>= for one machine, or =deploy .= for all.
